# D11.var02: DTIM=1 six-request boundary

This bounded CLI case derives from the accepted [DTIM=0 six-request control](../D11-var02-dtim-control-v1.0.0/README.md). Only `MaterielPM.DTIM` changes from 0 to 1, plus a description; the six mission requests and one-hour `MS4` task remain fixed. The manual permits a delay of `ceil(1×4)=4` extra missions before PM becomes critical. This schedule has only two requests after the fourth return, so it tests the noncritical state, not the eighth-return boundary.

The exploratory [probe contract](probe-contract.json) asked whether the PM would start and whether it remained noncritical. After observing its event timeline, the [exact acceptance contract](contract.json) was frozen and a separate guarded native run was executed. The probe and acceptance event logs and reports are byte-identical. The [evidence index](evidence-index.json) binds both local runs, source files, hashes and reviews; original SXI/SXO and reports remain under ignored `runs/`.

All six missions succeed. `MS4` is created and paused at hour 25, then remains labeled noncritical on the fourth, fifth and sixth returns. At the sixth return, hour 27.5, the log briefly reports the aircraft ready before the noncritical task resumes and performs one hour of PM work through 28.5. Relative to the accepted DTIM=0.3 case, this changes the status and same-time readiness events; the PM work interval and all 120 quantitative System/Stock bins are the same. Thus this run does not show PM postponed until the eighth mission, because no seventh or eighth mission is requested. Other schedules, DTIM/ATIM interactions, GUI-only behavior and cross-engine equivalence remain unverified.
