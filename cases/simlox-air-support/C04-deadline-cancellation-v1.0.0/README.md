# C04 1.0.0: fixed formation deadline and cancellation cleanup

This bounded case derives each input directly from a published [C03 1.0.2 input](../C03-shared-crew-formation-v1.0.2/README.md). It retains the same two-aircraft mission requirement, 07:30 order, 08:00 scheduled launch, and one 30-minute per-aircraft preparation using one P-CREW unit. The exact source changes are generated by `build.py` and stored under `parent-diffs/`. `OperationProfile.DTIM` defines the allowed launch delay; the manual also describes an earlier latest preparation-start check. This case tests both, using fixed deterministic inputs.

The [pre-native ledger](expected-ledger.json) and [initial contract](contract-discovery.json) were frozen before CLI work. The [reviewed contract](contract.json) records the five accepted variants and the failed horizon probe. The source-bound [validator](validate.py) checks per-aircraft events and all 72 half-hour system/resource rows. The [independent reviewer](review_readonly.py) is standard-library-only and does not import the builder or validator. The [evidence report](evidence-2026-09-29.md) lists accepted run IDs, hashes, tests and limits.

| Variant | Direct C03 parent | Only changed native fields | Native outcome |
| --- | --- | --- | --- |
| `crew-before` | `staffing-1` | `OperationProfile.DTIM=0.51` | Second aircraft ready 08:30, before 08:30:36 cutoff; launch 08:30. |
| `crew-equal` | `staffing-1` | `OperationProfile.DTIM=0.50` | Second aircraft ready at 08:30 cutoff; this fixed profile launches 08:30. |
| `crew-after` | `staffing-1` | `OperationProfile.DTIM=0.49` | Cutoff 08:29:24; partial second preparation stops, crew releases, mission cancels. |
| `aircraft-missing` | `staffing-2` | `SystemDeployment.QTYPS=1`; `OperationProfile.DTIM=0.50` | Only one aircraft can be assigned; it prepares and releases crew, then mission cancels 08:00. |
| `crew-zero` | `staffing-0` | `OperationProfile.DTIM=0.50` | Both aircraft wait for crew, no work occurs, mission cancels 08:00 and both waits stop. |

`horizon-wait` changes `Control.SIMPE` and `ResultCollection.RCEND` to 8 hours. SIMLOX rejected it with input conversion errors 107 and 204, producing no SXO. It remains a nonpublished probe at the same local `runs/` path; no horizon-end waiting claim is made.

Native runs are serial through the authenticated session-0 SSH wrapper and the `Global\SimloxIssue18NativeQueue` mutex. The runner verifies responsive SIMLOX GUI PID 13340 at preflight and confirms the same process remains after each native step. Run directories are immutable and ignored by Git; the raw inputs, SXI/SXO, ENLOG, report, invocation and closure remain on the local 4700-3 host. Do not commit them.

To reproduce the checked source locally, run `build.py --check`. To run a new native variant, call `invoke_loopback.ps1` through authenticated `ssh localhost` with a fresh `RunId`, one of the variant IDs and the input SHA-256 from `contract.json`. Each native job performs import, roundtrip export, calculation and JSON report export. The CLI evidence covers the stated fixed model only; no GUI-only or cross-engine behavior is asserted.
