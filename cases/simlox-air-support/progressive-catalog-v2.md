## 2. 渐进规则和实施顺序

`parent_case` 是建议派生源；`requires` 和 `instructional_prerequisites` 是完整的验收前置。原计划父例调整记录在 `original_parent_case/original_requires`；A01/A02 的冻结字段原样保留。表中“前置”去掉了重复的父例。只有父例和所用前置已按相应版本验收，才能发布派生例。

先取得一个可复核的最小基线，再沿依赖图推进。编号用于稳定识别，不能按字母数字顺序直接批量执行：例如 A04 需要 A09，D02 的日历分支需要 D06，G11 需要 D14，I07 需要 E15。

| 实施阶段 | 工作重点 | 出阶段要求 |
|---|---|---|
| 0 基线与工具 | 完成 A01/A02 GUI 交接；用 A01 校准 K01/K02/K07、J05 | 打开模型、回导、运行绑定、原始输出与事件可追溯 |
| 1 确定性任务和工序 | 近期并行推进 A03 编队基线与 B01→B02→C01→C02 资源链，在 C03 汇合；并行准备 B03 的显式任务类型合同；随后实施 A09/A04、C04、J07 | 手算时间线、需求数量、等待和释放可核对；B03 冷启动/热出动任务类型不可混用 |
| 2 任务与资源方法 | 逐项展开 A、B、C 的其他方法；暂缓尚缺物料/故障前置的条目 | 每项核心语义各有正常、边界和必要负例 |
| 3 故障、结构和物料 | D01/D06、G01/G02、E01 起步；按图展开 PM、库存、维修和初龄 | 两种故障/维修建模路线各自成立，实物与需求账闭合 |
| 4 网络与动态机制 | E 的供应网络，G 的 RBD，H 损伤，I 迁移与计划变更 | 排除不支持组合；同刻事件、期末状态和参数生效点有证据 |
| 5 综合与统计 | F01–F04；J01–J09；补齐 K 的交换和交付流程 | 固定合同、逐项回归、独立检索复现和单参数派生验收 |

每阶段只领取依赖已就绪的案例，前置不足的专项继续留在待办。K 是整个实施过程使用的方法，不能等到 F04 后才建立运行证据。

## 4. 边界变体与能力探针

579 是具名计划条目的数量，每条可以包含需要拆分的参数格子，不是 579 个已运行模型。落地时给每个具体格子分配稳定业务 ID、参数、预期时间线及独立运行 ID；首次证明关闭无关随机机制。

- **共用边界**：容量充足/不足/零，截止前/日志打印同刻/截止后，单需求/竞争，有库存/缺货/到货，终点在修/在途/预留，零分母。打印同刻不能证明内部事件优先级。
- **任务**：`MPAT` 的 FIXED/CONTINUOUS/EXTENDABLE 与 `ITYPE` 的 SCHEDULED/REGENERATIVE/RANDOM 是不同维度；先分别验证再组合。START 依赖、备用单位重试、默认周期公式需判别探针。
- **资源**：工序需求与 `MissionResource` 分开；资源类型使用 SPECIAL，专业按业务 RID 区分。C03 保留原合同：同编队两机、07:30 准备、每机30分钟，两人预期08:00、一人预期08:30起飞；必须逐笔核对申请、等待、占用、释放和起飞。
- **故障/PM**：传统 FRT 的 OPHOURS 路线与 FailureMode 的 CALHOURS 路线分开；MONIT 的个体维护另有结构限制。原生固定种子不能替代实际故障事件，更不能证明跨引擎随机流相同。
- **库存/网络**：区分名义库存和初始现货；`Control.ENBOP` 关闭时不能用 `BOPRI` 对照证明优先级。拆借、RRF/NFF 与显式维修路线的适用限制逐项记录。
- **结构和变更**：RBD 切换故障时钟仍待原生判明；I05 的边界是子工序是否已经开始，已开工主任务的后续未开工步骤可以采用新参数。14 张 `Changes*` 表逐项验证。
- **B03 显式任务类型合同**：`explicit-mission-type-v1` 以 `COLD-FIRST` 和 `HOT-SORTIE` 两个 MTID 表达首波冷启动和后续热出动，是本目录正式采用的业务替代方案，但仍待 4700-3 原生验收。同一 MTID 按历史出动序号自动切换未由手册确认，作为独立能力边界保留。

全部冲突与适用范围见[手册审读发现](known-issues/manual-review-v2.md)。既有 PM 时长、RSEED 类型、母子 FRT、零退出码无输出、J35 取消差异和 403 个嵌套 LRU 的物理换件问题继续保留。

## 5. 每例落地时的交付与验收

目录中的 `minimal_configuration` 是业务起点；`input_tables/checked_fields` 是来源已核对的候选映射，尚不是完整可运行原生模型。计划项的 `reproduce_command` 和 `artifact_ref` 留空，避免提供不存在的复现命令；A01/A02 指向已有包的 README。

每个案例实施前填写业务合同、显式单位、默认值、随机规则、停止条件和可手算时间线。每次只增加一个主要机制；复合选项拆为独立子变体。正常路径通过后再加入边界和组合。

| 交付记录 | 必需内容 |
|---|---|
| README / contract / parameters | 适用问题、父例版本、机制增量、实体/状态/事件、资源/库存、单位、参数和预期时间线 |
| mapping / 原生模型 / 生成器 | 表关系、全部非空业务行、稳定业务 ID、字段/默认值、GUI 入口及截图、SXI、原生 JSON、逐字段父子差分 |
| manifest / evidence-index | 程序版本及哈希、手册来源、输入/模型 SHA-256、种子/重复数/线程、不可覆盖的运行目录、取回方法 |
| 原始运行证据 | 实际命令、启动上下文、退出码、转换与回导日志、SXI/SXO/ENLOG、原始导出、逐项解释的警告 |
| acceptance / results-summary | 预期与实际事件、可执行断言、指标分母、资源账、可观察的实物/需求账、期末状态、失败及限制 |
| 复用指南 | 联动字段、真实复现命令、失败诊断、可变参数范围、扩展步骤及独立 agent 复验记录 |

原始导出保持字节不变；格式修复或规范化另存派生产物，同时记录原字节与规范化内容哈希。大型证据放在 4700-3 的版本化目录或受控存储，索引必须能在新工作区取回。

每次运行前检查 SIMLOX 进程；使用已经证明可用的启动上下文，保持每次运行独立目录。按 **GUI 校准 → 脚本派生 → 原生运行 → 自动核验 → GUI 复核** 推进。正常运行变体以导入回导、转换零错误、有效非空输出、可解析日志和警告解释为基本门槛；行为验收还要通过时间线、资源/库存和指标断言。非法输入负例以预期的原生拒绝及可定位诊断验收，保留失败产物，不要求生成有效 SXO，也不能标记为模型可运行。

状态按 **计划中 → 模型可运行 → 行为已验收 → 可复用发布** 推进，能力受限和跨引擎等价另设标记。未满足某项可观测性时明确缩小结论范围。随机案例先检查原生重复性，再按方差和目标精度安排样本；ENLOG 仅记录第一次重复，TCLEV 也只控制指定总任务时间统计。性能另记机器、线程、日志配置和阶段时间。

先找业务问题对应的最小案例，再检查 `status/verified_features/publication_state/limitations`；查到计划项只表示找到了下一步验证合同。原生已发布列表目前为空，A01/A02 的 CLI 证据仍需满足 GUI 发布门槛。
