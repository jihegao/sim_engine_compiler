# G04 three-branch active parallel threshold

This candidate extends the [accepted G04 active two-position input](../G04-series-active-parallel-v1.0.1/README.md) with a third installed position, POS-C. POS-C has the same LRU type and a leaf `G04-OPS` materiel mode, but no configured failure mode. The unchanged POS-A/POS-B failure modes provide the two possible distinct branch failures. Both arms operate all three positions (`NBOP=3`, `TSWOV=0`, `ONLM=N`); only the minimum required count changes from one to two. The long scheduled mission spans hours 8–34, so a second failure can occur before postmission direct CM. This is a fixed-seed test of the 1/3 versus 2/3 active threshold, not a population reliability estimate.

The source is frozen by `build.py`, parent input SHA-256 `ea56a9daf8705189c9162529355b28636ef7db168987b17ee90cdedbe9bb4b6f`, and `exact-diff.json`. Input SHA-256 is `cfdf287c4de93638e8117c71ad3de1846da3c62c24254bf7d2a3f0f7c7c0c4d7` for one-of-three and `38f85af4c121668eee3d31b07bb435b74571c5be6d63ddccff034549609ec319` for two-of-three. `contract.json` distinguishes native hypotheses from accepted behavior. Only eight existing tables change from the parent. Across the arms, only the problem description and `RBDParallel` description/`NBREQ` differ.

Both guarded native runs completed. The same POS-B and POS-A failure samples leave the one-of-three arm operational through its hour 34 success and make the two-of-three arm abort on the second failure at hour 16.7498. The [CLI sign-off](cli-scope-signoff-2026-10-02.md) gives the event and ledger evidence, independent 3,242-check GO, raw seals and limits.
