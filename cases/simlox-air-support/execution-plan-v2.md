## 2. 组织与所有权

| 角色 | 职责 | 不得替代的独立检查 |
|---|---|---|
| 主控 | 排依赖、分配工作区、维护门状态、汇总证据和阻塞；不兼任案例作者 | 不签署自己未独立复核的行为验收 |
| Tech lead | 冻结业务合同、审查父子差分、处理表关系和能力边界、决定是否退回开发 | 不用目录检查替代原生证据 |
| 案例开发 agent | 每个 agent 在独立工作区制作一个案例或一个无文件重叠的小组，提交合同、映射、原生输入和验收脚本 | 不修改其他 agent 的案例或共享冻结证据 |
| 自动测试 agent | 检查 schema、引用、父子差分、断言、哈希和证据索引 | 不判定 GUI 中不可观察的行为 |
| 独立 review agent | 从手册页码和父例重做合同审查，检查模型与引擎边界 | 不以作者说明代替产物检查 |
| 4700-3 执行组 | 唯一可操作原生环境的队列消费者，负责预检、导入/回导、运行、证据回收和 GUI 复核 | 不并行启动多个 SIMLOX 作业，不在远端临时修模型 |
| 验收 agent | 在回收的只读证据副本上独立执行断言并给出逐项结论 | 不接触运行目录，不重写原始输出 |

主控按实际可用 agent 数量调度，不预先声称并发席位。开发 agent 可以动态拆分手册审查、模型制作和验收脚本，但同一文件在一个阶段只能有一个写入者。共享目录文件由 Tech lead 在阶段末集中整合。

## 3. 证据状态和阶段门

每例使用以下状态，必须顺序晋级：

1. `planned`：目录合同、父例、前置、页码和候选表已定义。
2. `contract_ready`：业务合同、最小配置、单位、默认值、随机规则、停止条件和可手算时间线通过独立审查。
3. `model_ready_local`：原生输入、父子差分、生成/检查脚本和负例在本机完成静态校验。
4. `queued_for_native`：依赖案例已在所需范围通过，运行包有 SHA-256、版本和唯一运行 ID。前置未通过时只能进入隔离能力探针队列，不能取得此状态。
5. `native_runnable_cli` 或 `native_runnable_gui`：导入、回导、转换和运行产生有效非空输出；该状态只证明模型可运行。
6. `native_behavior_accepted_cli_scope` 或 `native_behavior_accepted`：实际事件、时刻、资源/库存账、指标和期末状态逐项满足合同。完整状态要求 GUI 门也通过。
7. `reusable_published`：复现命令、证据索引、适用范围和失败诊断经过独立复验并发布。

任何阶段都允许 `blocked` 或 `failed`，但必须保存失败输入、日志、退出码和诊断。进程退出码为零而输出为空、日志不可解析或证据目录被覆盖，均不能晋级。

`native_capability_probe_only` 是旁路证据标签，不是晋级状态。它允许在 GUI 或父例尚未通过时运行隔离的 CLI 探针，以定位表映射、可观测性和原生差异；探针结果不能签署父子行为验收、不能关闭前置，也不能发布为复用案例。

隔离运行可进一步以 `isolated_contract_cli` 标明已检查冻结合同中的 CLI 断言。该结果只归属于该输入、脚本和原生运行快照，必须同时保留 `publication_state=not_published` 与未完成的前置状态；即使全部断言通过，也不使目录案例晋级，不替代依赖链或 GUI 验收。

### 每例的开发门

- D0：父例版本和全部前置已解析，未通过的前置明确阻塞哪些断言。
- D1：合同只增加一个主要机制；业务 ID 稳定；手册页和表字段能反查。
- D2：原生模型、回导目标、父子字段差分和验收脚本齐全；无任意 Python 表达式或未声明默认值。
- D3：作者自测通过后，由独立 review agent 重跑静态检查和负例。
- D4：Tech lead 签署队列清单；主控才可移交 4700-3 执行组。

### 每例的原生验收门

- N0 环境：记录主机、SIMLOX 版本/哈希、许可证状态、启动上下文、活动进程和工作目录。
- N1 输入：记录传输前后哈希；只在唯一运行目录工作；先 data test，再导入和回导。
- N2 可运行：转换错误数必须为零，SXI/SXO/ENLOG 和所需报告有效且非空；警告逐项解释。
- N3 行为：逐事件和账本执行案例断言，不能只看汇总成功率或图形外观。
- N4 GUI：复核表关系、模型视图及案例要求的窗口/截图。无法执行时保持 CLI 范围状态。
- N5 回收：原始文件只读封存，生成 manifest、SHA-256 和取回路径；本机验收 agent 在副本上复跑断言。

## 4. 本机多 agent 流水线

每一批次按下列流水线运行。前两段可在无文件重叠时并行，后两段依赖前段输出。

```text
合同/手册审查 ─┐
               ├─> Tech lead 合同门 ─> 模型与脚本制作 ─┐
父例差分审查 ──┘                                      ├─> 自动测试 + 独立 review
验收断言设计 ──────────────────────────────────────────┘
                                                        ↓
                                              4700-3 串行队列
                                                        ↓
                                                独立证据验收
```

并行开发规则：

- 案例可使用独立 Git 工作区，或在同一任务分支按互不重叠的文件范围分配 agent；两种模式都要求单一文件写入者。共享目录、覆盖矩阵和检查器只由集成人员修改。
- agent 领取前先核对父例及前置状态；依赖未通过时可以完成合同和静态模型，也可进入隔离能力探针队列，但不能进入正式验收队列。
- 同一批可并行制作不同案例；父子案例的集成和原生运行仍按依赖顺序。
- 作者不能给自己的原生运行签署最终行为结论。验收 agent 使用回收后的只读证据。
- 每阶段末统一跑目录检查、目标案例测试和受影响的既有回归；只有失败定位到环境缺失时才可标为跳过，并写明缺失产物。

## 5. 4700-3 单一执行队列

4700-3 上只运行一个执行组和一个活动运行目录。该执行组消费两类串行队列：正式验收队列要求所有前置通过；隔离能力探针队列允许前置 GUI 或父例暂未通过，但必须写明待回答的单一问题和禁止晋级的范围。两类任务不得并行。每个队列项至少包含：队列类型、案例/变体 ID、父例版本及状态、输入包 SHA-256、SIMLOX 版本要求、GUI/CLI 步骤、超时、预期产物、验收脚本版本和回收目标。

执行顺序：

1. 只读预检主机身份、SIMLOX 版本、许可证、进程、磁盘和既有工作目录；发现活动作业则等待或记录冲突，不抢占。
2. 将已签署的本机包复制到新建的版本化运行目录，复核哈希。远端不接受临时编辑后的未登记输入。
3. 正式验收项按案例合同执行 GUI 校准及 CLI 数据检查、导入、回导、计算和报告。隔离探针只执行获批的最小步骤，并标记 `native_capability_probe_only`。GUI 与 CLI 结果分别记录。
4. 运行结束后先检查有效输出，再执行自动断言；失败时保留现场，不在同一目录重试。
5. 回收原始证据并将远端目录改为只读或等价冻结状态；下一队列项使用新目录。
6. 本机独立验收完成后才更新案例状态。需要复跑时创建新的 run ID，旧证据不覆盖。

队列优先级按“解除最多依赖、最小语义增量、失败可诊断”排序。紧急插队也必须等待当前作业完成和证据冻结。

## 8. 状态报告格式

每次 issue 更新分别报告：

- 已实现：本机已完成且进入相应开发门的合同、模型和脚本。
- 已验证：列出 4700-3 的具体 run ID、SIMLOX 版本、GUI/CLI 范围和通过断言。
- 失败或阻塞：列出失败步骤、原始诊断、保留产物和下一项最小实验。
- 仍计划：未进入原生队列的案例和依赖原因。
- 未验证：手册映射、设计预期、跨引擎等价和性能结论中尚无原生证据的部分。

目录静态检查、来源哈希、测试通过、模型能运行、CLI 行为验收、GUI 验收、跨引擎等价和性能测量是不同结论，报告中不得相互替代。
