# C09.var01 remote travel versus local resource wait

This three-arm teaching model derives from the C09.var04 local primary system-repair control, which in turn derives from C03 and D01. Two aircraft return from one scheduled mission with direct system failures at the same fixed-seed time. One `P-MECH` is at BASE-01 and another is at BASE-02. The first repair immediately occupies the local mechanic for 0.5 hour; the second repair initially waits. Each arm has the same borrowing route and differs only in forward trip time `ResourceRemoteSupport.TFRS`: 0.25, 0.5 or 0.75 hour. Return time is 0.5 hour and the direct repair task still has `ENRMS=Y`. `build.py`, `contract.json` and `exact-diff.json` freeze the input and parent delta.

All three arms completed guarded session-0 SSH native import, export, calculation and report export with GUI PID 13340 preserved. Native conversion had zero errors and only the inherited ENLOG #108 and no-item #126 warnings. Each import/export retained all 23 populated authored tables. The fixed-seed event logs show two failures at 8.53243 in every arm. At 0.25-hour forward travel, the remote mechanic travels from BASE-02 at 8.53243 and arrives BASE-01 at 8.78243, allowing the second repair to complete at 9.28243 while the first completes at 9.03243. One mechanic returns to BASE-02 from 9.03243 to 9.53243. At 0.5 and 0.75 hour travel there is no remote transport; the local mechanic serves the second repair after the first, completing at 9.53243. The native logs identify resource pools and quantities, not a persistent identity for each mechanic; the return event therefore demonstrates a one-unit pool return, not which physical person traveled back.

Each report has 72 aligned half-hour System, Stock and Resource bins. All three show two failures, two repairs and two ready aircraft at hour 36. Aggregate ResourceResults satisfy `NR + NRRT ≈ NRN = 4` in every bin. The short arm has 0.75 resource-hours in transit, matching its 0.25-hour outward and 0.5-hour return travel, and the equal and long arms have zero transit. Native reports are aggregated across resources/stations; station-specific movement comes from the event logs. One fixed seed and one replication support only this direct primary-repair threshold example, not every wait estimator, competing demand, other task types, GUI visual content or cross-engine parity. The bounded sign-off and independent replay are linked in `cli-scope-signoff-2026-10-02.md`.
