# E12: two symmetric operational bases

This bounded E12 case starts from accepted [E07](../E07-item-specific-transport-v1.0.1/README.md). The [frozen input](native-input.json) changes only the description, `Station.BASE-01.QTY` from 1 to 2, and `StockAllocation.BASE-01.STSIZ` from 0 to 1. The E07 item-specific FAST route, unit, aircraft deployment, mission schedule, depot stock, repair, seed and 36-hour horizon stay fixed. [Contract](contract.json) and [exact diff](exact-diff.json) were frozen before native execution.

Run `build.py` and `describe_diff.py` without flags to check source identity. The guarded `run_native_ssh.ps1` requires session-0 SSH, the host-wide Issue #18 mutex, source fingerprints and GUI PID 13340; its accepted run ID is `e12-symmetric-two-bases-v100-ssh-20261003-01`. `check_roundtrip.py` checks import/export identity. `validate_native.py` replays the event, ledger and report assertions, and `review/independent_replay.py` is a separate read-only replay. Raw native outputs stay in ignored `runs/`; the published [evidence index](evidence-index.json) records each path, size and SHA-256.

The two native instances are `BASE-01,0` and `BASE-01,1`, with separate `TEACH-UNIT` and aircraft instances and one opening spare at each base. The first failure occurs at base 0, whose local spare is consumed and replenished from the depot. Base 1's spare remains untouched. Each unit receives three mission opportunities. This source establishes the native `QTY=2` expansion behavior only. An explicit two-base comparator, station-group defaults and overrides remain separate E12 variants.
