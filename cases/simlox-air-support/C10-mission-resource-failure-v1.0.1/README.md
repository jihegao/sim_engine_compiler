# C10.var05: mission-held crew failure aborts a formation

This bounded pair derives from the accepted [C05 two-crew mission-resource case](../C05-mission-resource-v1.0.0/README.md) (capacity-two input SHA-256 `d2ea6e874eff82f1e50f271051010985c28adfba7aab94d2a0a0b343b989e865`). Both children extend the scheduled two-aircraft mission from two to five hours (8–13) and otherwise retain the same two `MISSION-CREW` units, one required per aircraft, seed 1 and 36-hour horizon. The failure child alone adds `ResourceStationData` for the crew at `BASE-01`: `RMTBF=3` hours, `RFTT=OPERATION`, `RMDT=0.25` hour. Descriptions label provenance. The [pre-run contract](contract.json) and [exact diff](exact-diff.json) fix these relationships. The installed manual (physical page 221, SHA-256 `39427027c46809a9ce9ebcb9be04e7396d96746e42a6f8c7c0ba2ddc294ef8a3`) says a resource failure assigned to a system on mission makes that system abort and return, with the mission requirement checked for whole-mission abort. The installed dictionary SHA-256 `11a61537c95489e32742d98ca8532b42aa1ec728c270009e5b1a8643325e96d0` defines the resource-failure fields.

An earlier frozen two-hour child under `C10-mission-resource-failure-v1.0.0` had no in-flight crew failure. That local diagnostic is excluded from this positive scope. The matched five-hour runs `c10-mission-five-hour-control-20260930-01` and `c10-mission-five-hour-failure-20260930-01` each completed guarded session-0 SSH import, export, calculation, JSON report and exact roundtrip of their 16 and 17 row-containing source tables under the host-wide Issue #18 mutex. GUI PID 13340/session 1 was preserved. Both converted with zero errors and expected warnings #108/#126. The native executable SHA-256 was `fe24c5bffc0c0641894bb335484cfb83993e3db2bd60122ddadfedd39a8c4db0`. Raw native artifacts remain ignored under local `runs/`; [evidence-index.json](evidence-index.json) binds original paths, sizes and SHA-256 hashes.

The control begins its formation mission at 8 and succeeds at 13. In the failure child, both aircraft start the same mission at 8, then a `MISSION-CREW` resource fails at 11.655 while assigned to aircraft 0. The native log explicitly records that aircraft aborting and the whole formation aborting at the same timestamp. Both aircraft return and are ready at `BASE-01` at 12.905. The failed crew is released on return and repaired at 13.155. The 1.5-hour failure-to-repair interval includes the 1.25-hour return; the configured 0.25-hour repair follows return. The log identifies the affected aircraft but does not expose a general worker-identity mapping.

Each report contains 72 half-hour resource, system and stock bins. Mission-held crew exposure is 10 resource-hours in the control and about 8.55994 in the failure child; failed crew exposure is zero versus 1.5 resource-hours. Both reserve two crew-hours before launch. Reported mission occupancy includes the return after abort; the failure report has `MSUF=0`, while `MTMF` and `STMF` are about 0.980994, so those latter fields must not be read as success counts. Both runs end with two ready aircraft, no aircraft failure and no stock movement. [Author replay](validate_native.py) checks the source delta, guarded execution, raw seals, exact roundtrip, failure/abort/return chronology, resource bins and terminal ledgers. A separate standard-library read-only replay is under `review/`.

This establishes one fixed-seed mission-assigned crew failure and formation abort on the installed executable. Other seeds, different mission resource types, partial formation requirements, GUI visual behavior, cross-engine equivalence and general C10 policy remain unverified. Issue #18 stays open.

To reproduce, run `build.py`, then invoke `run_native_ssh.ps1 -Variant five-hour-control -RunId <fresh-id>` and `-Variant five-hour-failure -RunId <different-fresh-id>` sequentially through session-0 SSH. Preserve the GUI and host mutex guards; every raw run is immutable.
