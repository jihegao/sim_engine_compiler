# Codex 云端建模实验结果

本轮已在云端工作环境中接入当前 Codex 会话的托管代理，实际完成 **需求/修改指令 → 规范化模型输入 → Business IR → Core IR → Execution Plan → 仿真 → 独立验收**。三组各 6 个可执行任务全部通过。本轮没有观察到机制卡或执行反馈提高验收率，题目已经出现满分上限，不能据此判断三条路线同样可靠。

## 实际检查了哪些行为

下列为 C 组最终轨迹中的关键观察，三组均通过同一组独立断言。时间单位为小时。

| 任务 | 机制 | 轨迹观察 |
| --- | --- | --- |
| T01 | 编队与有限资源排队 | staff 容量 2，第三架飞机等待；2.2 起飞，2.9 成功返航 |
| T02 | 分钟转小时 | 75 分钟转换为 1.25 起飞，42 分钟飞行后 1.95 返航 |
| T03 | 修改为串行准备步骤 | safety 在 2.22 完成，warmup 在 2.4 完成，2.4 起飞 |
| T04 | 提前取消与过期事件抑制 | tight 在 1.69 取消并释放占用资源；recovery 在 1.72 起飞；取消后无原作业的错误完成事件 |
| T05 | 成功完成依赖 | lead 在 2.4 成功返航，follow 同时满足依赖并起飞 |
| T06 | 外部故障、修理与飞行时钟维护 | 1.05 故障，1.9 中止返航，2.25 修理完成并开始维护，2.7 维护完成后执行下一任务 |

原有 bounded runtime 的 40 项合同测试通过。新增评分器的 16 项测试通过，包含六个手算正控、资源/单位/串行/取消/依赖/维护/故障七类错误变异，以及缩减模型、挪用运行结果、伪造过期完成事件等检查。这些测试有保存日志；未运行整个仓库的完整 CI 套件。

## 澄清后的追加演示

T07 首次响应询问缺失的 staff 容量。按实验前登记的模拟用户回答 `capacity = 2`，C 组另行生成完整模型，公开验证 1 次，无修订；独立验收通过，轨迹为 2.2 起飞、2.9 返航。

这不是一次真实用户补充输入，也不计入主实验结果。答复后的需求与 T01 相同，因此保留原始 T07 候选，另将副本的 `task_id` 改为 T01，使用已冻结的同一规格评分；这一重标记记录在 `secondary/T07/summary.json`。

T07/T08 的题目显式告知应澄清/返回 unsupported，不能用它们证明模型会自主识别缺失信息或能力边界。原评分器对两类文字使用字段/关键词检查；另将六份响应去除组别并固定种子洗牌，由新上下文的 AI 代理语义复核，六份均符合所给场景。这是 AI 复核，非人类审阅，也不是不同模型的独立佐证。原始得分未因复核改变。

## 对技术路线的判断

这一轮证明了现有 Codex 代理可以在云端驱动当前仓库的受限建模流程，并形成可追溯、可执行和可复查的 IR 证据。它没有建立持续托管的产品服务或外部模型 API 端点。

六道题参数明确，其中三道是给定模型的局部修改。模型输出的是规范化配置，Business/Core/Plan 三层 IR 由既有确定性编译器产生；尚未验证开放式问题抽象、机制发现、跨领域迁移或通用复杂系统可靠性。机制卡与 schema 有较多语义重叠，A/B 主要比较说明组织及补充示例，不能归因于真正的组合机制库或 MCP 架构收益。每组仅一个上下文、每题一次样本，组内任务存在上下文影响。

建议下一轮先提高实验辨别力：

1. 采用业务语言描述的留出任务，去掉字段名和预告的答题类型，分别评估需求澄清、机制选择、参数映射。
2. 加入未见机制组合、冲突需求与边界条件；用独立行为约束评分，避免只能匹配唯一完整配置。
3. 单独设定错误模型修复实验，比较相同修订次数下的编译反馈、轨迹反馈和最小反例反馈。
4. 增加任务与重复次数，控制工具预算，记录可用的明确模型版本、成本和人工干预时间，再判断机制库或微调是否值得投入。
