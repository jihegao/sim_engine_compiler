# Batch Plan preparation experiment for issue #6

This experiment compares the exact `e9b6391` runtime with the shared validated
Plan path. The primary real-case benchmark is the AMD128 `spare_mvp` J35
43-day, eight-aircraft Project export, frozen through the upstream
`SimulationAdapter.compile_scenario` into canonical simulation inputs. See
`results/amd128-j35-20260926/` for source hashes, Plans, acceptance and
measurements. The earlier F35 results in `results/amd128-20260926/` remain
historical evidence. `synthetic-capacity-16`
and `synthetic-remote-16` are prior synthetic workload fixtures.
`fixtures/shared-remote-pools` is the two-destination, shared personnel and
equipment supplier case generated by
`DependencyDispatchTests.shared_remote_pools(('personnel', 'equipment'))`.
Its Plan was compiled with the current three-layer Python/MLIR path and LLVM
23.1.1; the scan Plan removes only `resource_dispatch_index`. These synthetic
cases are not SIMLOX equivalence claims.

## Measurement boundaries

`run_cold.py` is the formal, uninstrumented end-to-end comparison: it warms
each configuration once, then launches a new `sim-engine-runtime` process for
each of six paired repeats and reverses A/B order on alternating rounds. Its
process wall includes startup, Plan-file read/validation, execution and pretty
JSON output. The OS page cache is not flushed. It hashes and removes each
large output. Complete batch bytes must match across dispatch arms, repeats,
and builds for each worker count; sample results must also match across worker
counts. Resource indexes do not change the semantic Plan fingerprint.
The CLI's final `samples` JSON field is hashed as a byte range, so Full
results can be checked without loading multi-gigabyte output into Python.

`run_benchmark.py` uses the unchanged `stage-c-benchmark` binary for segmented
diagnostics in two clean checkouts. Each invocation warms once and measures
one repeat. It requires identical Plan and input hashes and compares complete
serialized sample results across all arms, threads, repeats, and builds. Its
`end_to_end_batch_ns` includes Plan read/parse/validation, batch work,
serialization, and file write; process startup and compilation are excluded.
`batch_execution_ns` begins after Plan load and includes per-call preparation,
thread-pool setup, sample initialization, and execution. RSS is the maximum for
the entire benchmark process, including warmup and separate single-sample
measurements; do not interpret it as an isolated RunState allocation.

The checked-in diagnostic patches apply only to separate copies of the two
checkouts. They add atomic phase counters and one stderr record per CLI batch.
Use their results for attribution, not timing comparisons with the unpatched
binaries. The baseline patch counts batch validation/static preparation and
sample validation/static preparation/total initialization. The candidate patch
counts one preparation validation/static build and sample initialization.
Both patches also split JSON Plan read, parse, validation, and fingerprint in
the CLI loader; this diagnostic branch applies to Plan JSON rather than binary
Plan caches. Compile, serialization, and write times come from the uninstrumented
Stage C report. The hot benchmark compares repeated public calls with repeated
calls against one `PreparedBatchPlan` in the candidate binary; each pair
checks exact sample output hashes.
After applying the patches to separate checkouts and building their CLI
binaries, `run_diagnostic.py` records the phase counters, patch/binary hashes,
and identical full results for 32/256 samples at one thread.
`run_hot.py` drives the uninstrumented `prepared_batch_benchmark` across the
same batch sizes and worker counts; its reports retain six paired calls,
one-time preparation, serialization and whole-process peak RSS.

## Reproduction on AMD128

For J35, use the committed `spare_mvp` export at upstream
`0e709bdcc2d692d9cfed49b9037c76ef71aefe33`, not a local project database.
Run `export_spare_mvp_case.py` in the upstream Python environment with
`--project-json exports/project-case-large.json`; the checked-in
`results/amd128-j35-20260926/source/manifest.json` gives its source,
schema and canonical hashes. Compile the canonical JSON through
`scripts/compile_execution_plan.py --semantic-profile event-time-v2` for the
scan Plan. The indexed Plan uses `scripts/compile_mlir_execution_plan.py`
with the pinned LLVM/MLIR 23.1.1 plugin. Keep both Plan files byte-identical
to the checked-in J35 fixture before benchmarking.

Create isolated checkouts of `e9b6391` and the candidate commit from Git
bundles or the remote repository; do not benchmark an older AMD128 checkout.
Build each with `cargo build --offline --locked --release --manifest-path
rust/runtime/Cargo.toml --bin stage-c-benchmark --bin sim-engine-runtime`.
Run the formal matrix from the candidate checkout:

```bash
python3 benchmarks/batch_preparation/run_cold.py \
  --baseline-root /path/to/e9b6391 \
  --candidate-root /path/to/candidate \
  --case-dir /path/to/j35/fixture \
  --cases j35 --levels summary \
  --output /path/to/evidence --repeats 6
```

Measure O5 + Summary first, and Full separately. Counts are 1, 32, and 256;
batch worker counts are 1/2/4/8 (one worker for a single sample). `scan` uses a
Plan without the index; `cache` and `candidates` use the same v2 index with
candidate dispatch off/on. No dispatch algorithm changes are part of this
experiment. Preserve the JSONL records, Stage C reports, identities, toolchain
versions, binary/input/Plan hashes, and diagnostic patch hashes with the final
report. Report Python binding timing separately from Rust CLI timing.

Run:

```bash
python3 benchmarks/batch_preparation/summarize.py \
  /path/to/evidence/records.jsonl --output /path/to/evidence/summary.json
```

This retains every paired gain and RSS ratio. A row passes the predefined adoption gate only
with at least six pairs, positive gains in every pair, median gain of at least
5% and greater than either arm's relative median absolute deviation, and no
repeated peak RSS increase above 5%. Report all thread counts and
cases even if only the J35 O5 + Summary rows determine default-path adoption.

Canonical-to-Plan compilation remains a separate measurement. Use
`run_benchmark.py` for stage timing on representative cells and
`prepared_batch_benchmark` for repeated use of one prepared Plan handle.

After building and installing each checkout's Linux PyO3 extension into its
own `.venv`, use `run_binding.py` for paired `run_batch(plan_bytes, seeds)` calls.
It records extension/Plan hashes and measures native parsing, batch execution,
result transfer and Python JSON decoding inside the call. Plan file reading and
Python process startup are excluded; candidate dispatch is not exposed by this
Python API, so the binding comparison uses scan or v2 cache mode.

`run_compile.py` records current canonical-to-three-layer-to-MLIR Plan
compilation on the macOS host with the pinned LLVM 23.1.1 plugin. It asserts
that regenerated Plans are byte-identical to the frozen runtime inputs. Its
process-wall numbers are a separate one-time cost and must not be divided into
AMD128 runtime numbers or presented as an AMD128 compiler measurement.
