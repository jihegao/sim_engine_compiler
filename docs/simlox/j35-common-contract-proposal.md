# J35 可比较共同合同提案 v0.1（未批准）

本文件是待业务/架构审查的版本化提案，不修改已接受的 Python reference、固定 `legacy-minute-v1` Execution Plan 或原始 SIMLOX 模型。两项差异须分别验收；通过一项不能豁免另一项。

## C1：派遣取消与起飞前准备

固定合同在派遣阶段按 `minute - planned_start >= cancel_minutes` 取消。phase7 的八 SID PM-only 20 波反例中，原生在第 20 波 `176.967 h` 取消并停止正在进行的准备；固定 Python/Rust 到 `179 h 20 min` 才取消。原生时刻与 `STIM+DTIM−142 min` 相符。有效原生小探针表明：两架已选齐、仅共享资源拖慢准备时，取消可延至 `STIM+DTIM`；两架均被前一波占用、尚无可选飞机时，原生日志明确给出 `STIM+DTIM−142 min` 等待超时。修正的八格通过实际 PM 作业时长判别：第二架在截止前完成可起飞、截止后完成取消，打印同刻时日志先取消后 PM 完成；DTIM、准备步骤时长和零准备改变，均使日志超时按 `STIM+DTIM−总准备时长` 移动。这仍不证明所有内部同刻优先级或普遍动态算法。

候选 v0.1 的问题是：业务是否要求「未选齐飞机时用可行准备启动截止；选齐后允许准备/资源等待到 `STIM+DTIM`」，以及晚到第二架、共享资源阻塞、已开始准备取消后的资源释放，如何排序？如采用此规则，应在 Business IR 明示时限含义，经 Core Simulation IR 编译为独立语义配置与新版本 Execution Plan，给 Python/Rust 加行为测试并从 104 波重验。不得通过私调原生 `DTIM` 或准备时长改写现有 J35 输入。若维持固定合同，应寻找有证据的原生配置使其按现行取消时刻运行；目前未找到。

## C2：403 个嵌套 LRU 的实物换件边界

canonical 与固定 Plan 有 403 个明确 LRU 产品、20 个未标型中间组件。Python/Rust 当前在失败 LRU 的 `replacement` 修理步骤请求**该失败产品** 1 件，父组件链只用于失效传播；Plan 并未暴露坏件拆下、父件备件、车间换子件或返回仓库的完整物理账。全部 403 个 LRU 位于飞机根下第 2/3 层。SIMLOX 文档把一级系统可换件 LRU/PRU/DU 与车间二级 SRU/SPRU/DP 分成不同交易；phase6 的 PRU→SPRU 能力切片不证明与这 403 个 Plan LRU 同义。

需要上游业务决定每个源产品的直接拆装单位、是否领父件、父件/子件的库存品类与库位、拆下件去向、维修/报废/外援回流、年龄复位和 PM 相互作用。若源规则为「嵌套 LRU 在飞机上直接换件」，原生投影须逐类证明能维持相同系统装机、共享库存与维修路线；若实际应领父级组件，则现有 Plan/Python 合同要独立版本化更改并重新验收，不能把 403 LRU 静默改作 SRU/SPRU。

## 独立验收门槛

1. C1：原生最小取消矩阵各格导入/回导/ENLOG 有效；区分何时开始、完成、取消与释放；104 波 PM-only 全程事件一致。
2. C2：以可控同一故障时刻覆盖现货、零库存、争抢、回库再领、兄弟件、PM 和终点欠交；记录按产品及装机实例的物料/需求守恒与维修路径。403 项逐项有业务映射。
3. 两项都通过后，另验故障、资源、停止和输出口径，再预注册独立 RNG 的分布指标、容限与样本量；通过后才有等价性能比较资格。

当前状态：**C1 既有反例确定性不通过；C2 完整物理合同未定义、未验证。** 协调端已使首版 12 格和修正 8 格原生取消矩阵有效运行，后者补足第二架临界返回的条件化证据。`p2c-*` 六格有效原生换件探针证明一件共享顶层 PRU 现货争抢、欠交、二级修理回流和再领；其 PRU→SPRU 交易仍不能无损投影到固定 Plan 的 403 个嵌套 LRU。没有修改现行业务合同。
